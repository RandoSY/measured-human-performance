# FFT — Fair Fitness Tester for Android

Native Android/Kotlin prototype for a controlled step fitness test.

## What is implemented

- Participant setup: name/ID, age, sex/category, body mass, body height.
- Test prescription: target external mechanical power (W), physical step height, duration.
- Transparent cadence calculation: `P = m g h f`.
- Four-beat stepping pattern: **UP · UP · DOWN · DOWN**.
- Standard Bluetooth LE Heart Rate Service scanning/connection and live HR notifications.
- Works with standards-compliant chest straps; Polar H10/H9 use the standard BLE Heart Rate Service.
- Explicit HR hard-stop ceiling required before the test can start.
- Immediate test/metronome stop when received HR reaches or exceeds that ceiling.
- Safety stop if the HR stream is lost for >8 s during a test.
- Phone accelerometer/linear-acceleration capability check.
- Android hardware `TYPE_STEP_DETECTOR` support when available, with live step count and observed cadence.
- Compliance score compares detected footfalls and observed cadence with the commanded four-beat cue.
- Local-only SharedPreferences storage. No account, cloud, analytics, ads, or network permission.
- Material 3 dark navy/cyan visual system and custom adaptive launcher icon.
- Unit tests for cadence physics and standard BLE HR packet parsing.

## Power model

For a participant with mass `m` kg, step rise `h` m and requested external mechanical power `P` W:

```
cycles_per_min = 60 P / (m g h)
metronome_bpm  = 4 * cycles_per_min
```

The model counts positive gravitational work during ascent. It does **not** attempt to estimate metabolic power, efficiency, or negative work on descent.

## Safety behavior

The app deliberately does **not** invent an age-predicted maximum HR. An explicit ceiling must be entered from the intended protocol/clinical guidance. During an active test:

1. `HR >= entered ceiling` → immediate software stop.
2. HR BLE sensor disconnects → immediate software stop.
3. No HR update for 8 seconds → immediate software stop.
4. Manual STOP is always visible on the test screen.

“Stop” means the app stops cadence cues, timing and recording and displays the reason. A phone cannot physically stop a participant from continuing to move.

This is a prototype fitness-test controller and is **not a medical device**.

## Phone placement / compliance

Use a snug front trouser pocket or waist pouch, with the phone secured rather than loose. Hardware step detection is preferred. Linear acceleration is also monitored as a motion sanity check. The compliance channel is appropriate for confirming that the test was performed at approximately the commanded cadence; it is not a substitute for force plates or laboratory motion capture.

## BLE details

The implementation filters scan results for Bluetooth SIG Heart Rate Service UUID `0x180D`, subscribes to Heart Rate Measurement `0x2A37`, and parses both 8-bit and 16-bit HR values per the standard characteristic flags.

Android 12+ uses `BLUETOOTH_SCAN` and `BLUETOOTH_CONNECT`. Android 10+ requires `ACTIVITY_RECOGNITION` for the hardware step detector. Older Android versions use legacy BLE/location permissions.

## Build

Recommended current toolchain:

- Android Studio Quail/Panda generation or newer
- JDK 17+
- compileSdk / targetSdk 37
- Android Gradle Plugin 9.2.1
- Kotlin 2.3.21
- Compose BOM 2026.08.00

Open this folder in Android Studio, allow Gradle sync to download dependencies, connect an Android phone, then Run `app`.

No APK is included because this build environment does not contain the Android SDK; the source project is complete and ready for Android Studio compilation.

## First real-device test checklist

1. Update the Polar H10/H9 firmware using Polar Flow.
2. Wear the moistened chest strap.
3. Launch FFT and grant Nearby devices + Physical activity permissions.
4. Setup: enter mass, step height, target watts, duration, and a protocol-approved HR ceiling.
5. Sensors: scan and select the Polar device.
6. Confirm live HR.
7. Secure the phone in a front pocket / waist pouch.
8. Start FFT and verify the 4-beat cue corresponds to UP · UP · DOWN · DOWN.
9. Perform a low-intensity validation run before any higher workload testing.
10. Verify the HR hard stop with a deliberately low temporary ceiling during bench testing (do not exercise to provoke a high HR).
